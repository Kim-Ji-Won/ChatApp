# ChatApp 통신 v1 — 공동 검토용 초안

상태: **백엔드 담당자와 합의 전**. 현재 프론트엔드와 데모·테스트 상대가 사용하는 규칙입니다. 기존 서버 규칙이 정해져 있다면 이 문서와 `Message`, `SocketTransport`를 함께 조정합니다. 최종 규칙으로 일방 확정하지 않습니다.

## 전송 형식

- TCP 연결 하나를 유지합니다. 기본 포트 제안: 5000.
- 프레임: `4바이트 길이(big-endian 정수)` + `길이만큼의 UTF-8 payload`.
- payload: `TYPE` 뒤에 필드가 있으면 탭으로 구분한 **각 문자열의 UTF-8 Base64**를 붙입니다.
- 종류는 `[A-Z_]{1,32}`. 길이는 1~65,536바이트. 줄바꿈 종결자는 없습니다.
- 빈 문자열은 빈 Base64 필드입니다. 마지막 빈 필드도 보존합니다.
- 공통 `Message.read/write`를 재사용할 수 있습니다. 프레임 하나를 다 읽은 뒤 다음 프레임을 처리합니다. Java 객체 직렬화는 사용하지 않습니다.
- 아래 표의 필드는 **디코딩된 문자열** 기준입니다. 정수 값도 문자열로 전달합니다.

예: `ROOM_JOIN`의 roomId가 `r1`이면 payload는 `ROOM_JOIN\tcjE=`이고 UTF-8 길이는 14바이트입니다. 실제 탭 한 바이트를 사용합니다.

## 클라이언트 → 서버

| 종류 | 필드 순서 | 의미 |
|---|---|---|
| HELLO | nickname | 연결 직후 닉네임 등록 |
| ROOM_LIST | 없음 | 최신 방 목록 요청 |
| ROOM_CREATE | name | 방 생성 후 해당 방 입장 요청 |
| ROOM_JOIN | roomId | 기존 방 입장 요청 |
| ROOM_LEAVE | 없음 | 현재 방 퇴장, 연결은 유지 |
| CHAT_SEND | text | 현재 방 메시지 전송 |

요청에 포함된 사용자명으로 권한을 판단하지 않습니다. 서버는 해당 연결에 등록된 사용자와 현재 방을 기준으로 처리합니다.

## 서버 → 클라이언트

| 종류 | 필드 순서 | 수신 대상·처리 |
|---|---|---|
| WELCOME | nickname | 접속 성공, 본인에게 1회 |
| ROOMS | roomId, name, count 반복 | 전체 방 목록 스냅샷. 방이 없으면 필드 0개 |
| ROOM_JOINED | roomId, name | 방 생성·입장 성공, 요청자에게 |
| ROOM_LEFT | 없음 | 퇴장 성공, 요청자에게 |
| ROOM_USERS | roomId, nickname 반복 | 해당 방의 전체 참가자 목록 |
| CHAT_MESSAGE | roomId, sender, text | 해당 방 전체, **보낸 사람도 포함** |
| SYSTEM | roomId, text | 해당 방의 입장·퇴장 등 안내 |
| ERROR | code, description | 요청 실패, 요청자에게 |

## 서버가 보장할 순서

1. 접속 성공: `WELCOME` → `ROOMS`. WELCOME 전에 방 이벤트를 보내지 않습니다.
2. 닉네임 등록 실패: `ERROR`를 전송하고 연결을 종료합니다.
3. 방 생성·입장 성공: 요청자에게 `ROOM_JOINED` → `ROOM_USERS`. 그 뒤 방 안내·채팅을 보냅니다. 방 목록과 인원수 변동은 `ROOMS`로 갱신합니다.
4. 퇴장 성공: 요청자에게 `ROOM_LEFT` → `ROOMS`. 남은 방 참가자에게 `ROOM_USERS`를 보냅니다.
5. 채팅 성공: 보낸 사람을 포함한 같은 방에 `CHAT_MESSAGE`를 보냅니다. 이 이벤트가 전송 성공 응답입니다.
6. 요청 실패: 성공 이벤트 대신 `ERROR`를 보냅니다. 실패한 요청으로 서버 상태를 변경하지 않습니다.
7. 방 생성·입장·퇴장·방 삭제로 방 목록이나 인원수가 바뀌면 접속자 전체에게 `ROOMS`를 보냅니다. 방 안의 사용자도 받습니다.
8. 접속이 끊기면 방에서 제거하고, 남은 참가자에게 `SYSTEM` → `ROOM_USERS`를 보낸 뒤 접속자 전체에게 `ROOMS`를 보냅니다.
9. 접속 후 5초 안에 `HELLO`가 없거나 `HELLO` 전에 다른 요청이 오면 서버가 연결을 종료합니다(후자는 `ERROR(UNSUPPORTED)` 후 종료).

1주차 클라이언트는 동시에 하나의 화면 요청만 처리합니다. 서버 응답 대기 중 관련 버튼은 비활성화되고 7초 동안 응답이 없으면 연결을 종료합니다. 접속·HELLO 응답에는 각각 5초 제한이 있습니다. 이후 비동기 요청을 확대할 때 requestId 추가를 함께 검토합니다.

## 입력·오류 기준

- 닉네임: 앞뒤 공백 제거, 1~20 UTF-16 코드 단위. 제어문자 불가. 중복은 서버에서 거부.
- 방 이름: 앞뒤 공백 제거, 1~40 코드 단위. 제어문자 불가.
- 채팅: 앞뒤 공백 제거, 1~1000 코드 단위. 현재 UI는 한 줄 입력이며 제어문자 불가.
- 방 ID는 서버가 발급한 불투명 문자열입니다. 표시 이름으로 방을 구분하지 않습니다.
- 서버는 클라이언트 검사와 관계없이 길이·권한·현재 방 상태를 다시 검증합니다.
- 오류 코드 제안: `NICKNAME_TAKEN`, `INVALID_NICKNAME`, `INVALID_ROOM`, `ROOM_NOT_FOUND`, `NOT_IN_ROOM`, `INVALID_MESSAGE`, `UNSUPPORTED`.
- 백엔드 구현 기준(공동 확정 사항, 지원님 확인 후 확정):
  - 한 사용자는 한 방에만 있습니다. 방에 있는 상태의 `ROOM_CREATE`/`ROOM_JOIN`은 `ERROR(INVALID_ROOM)`입니다. 방을 바꿀 때는 `ROOM_LEAVE` → `ROOM_LEFT` 확인 후 `ROOM_JOIN` 또는 `ROOM_CREATE`를 요청합니다.
  - 참가자가 0명이 된 방은 서버가 삭제하고, 삭제 사실은 `ROOMS` 목록에서 사라지는 것으로 전달합니다.
  - 닉네임은 접속 중에만 중복을 막습니다. 접속이 끊기면 같은 닉네임을 다시 사용할 수 있습니다.

## 다음 주 확장

귓속말, 게임, 이모티콘, 일정 메시지는 아직 구현하지 않았습니다. 각 기능을 시작하기 전에 필드·성공 응답·오류·수신 대상부터 추가 합의합니다. 서버 저장 방식도 별도 합의합니다.
